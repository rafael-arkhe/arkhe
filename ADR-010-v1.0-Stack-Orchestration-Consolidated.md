## 1. Contexto

O ecossistema Arkhe acumulou **três stacks de orquestração paralelas** em documentos que deveriam ser convergentes:

| Documento | Stack | Licença | Escopo |
|---|---|---|---|
| ARKHE-3DP-LITHOGRAPHY-MLOPS v3.1 | Kubeflow / Airflow + MLflow + Feast | Apache 2.0 | MLOps industrial para litografia 3D |
| Plano_Nacional_Producao_Hardware v2.0 | Palantir Foundry + Ontology + AIP | Proprietário | Camada enterprise de integração |
| ADR-009 v1.1 | Windmill | AGPLv3 | Orquestração externa opcional |
| SISBIN-TRIADE v1.0 | Kafka (KRaft) + OpenLineage + MinIO + PostgreSQL | Apache 2.0 / MIT / PostgreSQL | Infraestrutura de dados federada |

**Problema:** Submissão à Finep Rodada 2 (prazo: 30/09/2026) não pode apresentar stack indefinido. A inconsistência arquitetural é vetor de reprovação técnica (critério Finep: "inovação tecnológica real com plano de execução coerente").

**Forças em tensão:**
- **Soberania tecnológica:** preferência por open-source com governança nacional.
- **Maturidade operacional:** Palantir oferece cases verificados (Mercury Systems, semicondutores), mas com lock-in estrutural e custo proibitivo para escala acadêmica.
- **Agilidade de prototipagem:** Windmill oferece git-sync e durable execution, mas AGPLv3 cria risco de contaminação de licença e não substitui runtime científico.
- **Convergência institucional:** SISBIN já define Kafka + OpenLineage como padrão de linhagem; desviar disso cria incompatibilidade com governança federal.

### 2.2 Regras de Ouro (Invariantes)

| # | Invariante | Consequência de Violação |
|---|---|---|
| R1 | **Kubeflow é o runtime primário de pipelines ML.** Windmill nunca executa código de treinamento, inferência ou simulação científica. | Remoção imediata de Windmill; revisão de ADR-009. |
| R2 | **MLflow é o único Model Registry autorizado.** Nenhum artefato de modelo entra em produção sem registro em MLflow com assinatura Ed25519 (futuro: ML-DSA-65). | Pipeline bloqueado no CI/CD. |
| R3 | **Kafka + OpenLineage são a infraestrutura de dados obrigatória para projetos com funding público (Finep, BNDES, FAPs).** | Incompatibilidade com auditoria do TCU/CCAI. |
| R4 | **Palantir Foundry/Ontology/AIP são REJEITADOS como stack primário para Frente A (Finep 2026) e Fase 0–2 do PNH.** | Reabertura desta ADR requer: (a) PoC com ROI demonstrado em 2 órgãos; (b) aprovação Legal de lock-in; (c) orçamento aprovado fora da linha Finep. |
| R5 | **Toda imagem Docker no stack é PINADA por digest SHA256.** Tags mutáveis (`:latest`, `:main`) são proibidas. | Reprovação no code review; rollback automático. |
| R6 | **AGPLv3 é blacklist para linking ou modificação.** Windmill executa como processo separado via webhook/gRPC, nunca como crate/biblioteca linkada. | Parecer Legal obrigatório; se rejeitado, Windmill removido sem impacto funcional. |

### 2.3 Posicionamento de Componentes Descartáveis

| Componente | Status | Condição de Remoção |
|---|---|---|
| **Windmill** | ✅ Mantido (ADR-009) | Legal rejeita AGPL; ou latência EvidenceBus degradada; ou PR injeta Windmill no runtime. |
| **Palantir** | ❌ Não selecionado | Nunca selecionado para Frente A. Reavaliação possível em 2030+ com PoC, CASD e funding separado. |
| **Airflow** | ✅ Mantido como fallback | Substitui Kubeflow apenas em workflows de dependência complexa (DAGs com 50+ tasks). |

## 3. Justificativa

### 3.1 Por que Kubeflow + MLflow + Feast?

| Critério | Kubeflow/MLflow/Feast | Palantir | Windmill |
|---|---|---|---|
| **Soberania** | ✅ Código aberto; governança CNCF/LFAI | ❌ Proprietário; lock-in estrutural | ✅ Código aberto; mas AGPLv3 restritivo |
| **Custo de escala acadêmica** | ✅ Zero licença; custo infra apenas | ❌ US$ 500k–2M/ano (estimativa) | ✅ Zero licença |
| **Maturidade MLOps** | ✅ Padrão de mercado; cases em produção | ✅ Enterprise maduro | ⚠️ Orquestração, não MLOps científico |
| **Convergência SISBIN** | ✅ Kafka/OpenLineage nativos | ❌ Requer conectores customizados | ⚠️ Requer bridge (ADR-009) |
| **Licença compatível com Arkhe MIT/Apache** | ✅ Apache 2.0 | N/A (proprietário) | ❌ AGPLv3 — processo separado obrigatório |
| **Pipeline de CI/CD reprodutível** | ✅ Helm charts; containers pinados | ❌ Black box; updates controlados pelo vendor | ✅ Docker compose; mas tag `:main` era risco (corrigido v1.1) |

### 3.2 Por que Palantir foi Rejeitado como Primário

O Plano Nacional de Hardware v2.0 posiciona Palantir como "camada enterprise opcional". No entanto, para a **Frente A (Finep 2026)** e as **Fases 0–2 (2026–2029)** do PNH, Palantir é **arquiteturalmente inadequado**:

1. **Custo:** Orçamento de R$ 5–8M (Finep) não absorve licenciamento Palantir + FDEs (Forward Deployed Engineers).
2. **Lock-in:** Migração de Ontology objects é não-trivial; a Finep exige sustentabilidade pós-projeto.
3. **Over-engineering:** Para 3 laboratórios com OpenCAL + MQTT local, Palantir é "canhão para matar mosca" (própria avaliação do v2.0, Seção 5.3).
4. **Soberania:** Vendors EUA sujeitos ao CLOUD Act; dados de litografia 3D, mesmo não-classificados, são ativos estratégicos sob PL 2.780/2024.

> **Nota:** Palantir permanece como **nota de visão 2030+** no PNH. Se a Plataforma Unificada (P9) for viabilizada em 2030+, uma PoC Palantir pode ser reavaliada pelo CASD (Conselho de Arquitetura de Soberania Digital) com funding separado (BNDES, não Finep).

### 3.3 Por que Kafka + OpenLineage são Obrigatórios?

O SISBIN-TRIADE v1.0 (Parte I, Seção 4.2) define Kafka + OpenLineage como stack de linhagem para a PDF-SISBIN. A Frente A, embora não seja projeto SISBIN, **antecipa** a conformidade com a governança federal de dados:

- **Kafka KRaft:** Elimina dependência do ZooKeeper; modo hardened com TLS 1.3 + mTLS inter-broker.
- **OpenLineage:** Padrão emergente para lineage de dados; integra nativamente com MLflow (runs) e Kubeflow (pipelines).
- **MinIO:** Object storage S3-compatível que roda em bare metal; soberano operacional; replicação cross-site via Ceph/Rook (futuro AMSR).

## 4. Consequências

### 4.1 Positivas

- **Consistência inter-documental:** v3.1, SISBIN-TRIADE e ADR-009 convergem para um único stack primário.
- **Reprodutibilidade:** Helm charts oficiais do Kubeflow + MLflow permitem deploy idêntico em LNNano, CTI e UFRGS.
- **Auditabilidade:** OpenLineage gera lineage automático para cada run do Kubeflow; CCAI pode auditar sem acesso ao código.
- **Escalabilidade:** Stack suporta 3 laboratórios (2026) → 50+ municípios (2029) sem reescrita arquitetural.

### 4.2 Negativas / Guardrails

- **Complexidade operacional:** Kubeflow requer expertise Kubernetes; laboratórios acadêmicos podem precisar de suporte da RNP.
- **Latência de warm-up:** Primeiro deploy de pipeline Kubeflow pode levar 5–10 min (container pull + init); não adequado para inferência em tempo real <100ms (use arkhe-inference nativo).
- **Curva de aprendizado:** Feast requer modelagem de features; equipe precisa de capacitação (budget: 3 meses de residência).

## 5. Alternativas Rejeitadas

| Alternativa | Razão de Rejeição |
|---|---|
| **Palantir como stack primário** | Custo proibitivo (Finep R$ 5–8M); lock-in estrutural; CLOUD Act; over-engineering para 3 laboratórios. |
| **Windmill como substituto do Kubeflow** | AGPLv3; não é MLOps pipeline (falta Model Registry, Feature Store, experiment tracking); categoria errada. |
| **n8n / Activepieces** | n8n fair-code (SUL) bloqueia redistribuição comercial; Activepieces é visual builder inadequado para batch científico. |
| **Apache NiFi + Ranger (substituto SISBIN)** | NiFi é legado; Ranger não suporta ABAC baseado em DID; incompatível com Evidence Bus. |
| **GitHub Actions + self-hosted runners como orquestração** | Não é MLOps; falta lineage nativo; vendor lock-in Microsoft; não soberano. |

## 6. Roadmap de Implementação do Stack

### Fase 0 — Finep 2026 (3 laboratórios)
```yaml
infraestrutura:
  - Kubernetes single-node (k3s) por laboratório
  - Kubeflow Pipelines (lightweight, sem Istio)
  - MLflow Tracking + Model Registry (PostgreSQL backend)
  - Kafka single-node (KRaft) para ingestão MQTT
  - MinIO single-node para artefatos
  - OpenLineage + Marquez (opcional, pode ser postergado para Fase 1)

custo_estimado_por_laboratorio:
  hardware: R$ 15.000  # servidor edge + storage
  software: R$ 0        # open-source
  capacitacao: R$ 30.000 # residência MLOps 3 meses
  total_3_labs: R$ 135.000
```

### Fase 1 — Consolidação (2027–2028)
- Expandir para Kafka cluster (3 brokers) com replicação entre LNNano e CTI.
- Adicionar Feast (feature store) após acúmulo de dados suficientes (N > 10k prints).
- Integrar Evidence Bus (arkhe-evidence-bus) ao pipeline Kubeflow via webhook.

### Fase 2 — Escala (2029–2031)
- Kubeflow multi-tenant com OPA para isolamento por órgão.
- MinIO federado cross-região (AMSR Fase 2).
- libharpia substitui Ed25519 em MLflow signatures e Evidence Bus.

## 7. Critérios de Reavaliação

Esta ADR será reavaliada semestralmente ou quando ocorrer:

1. **Mudança de status de libharpia:** Se libharpia atingir TRL 7 (verificação formal Kani/Coq em escala), reavaliar criptografia do stack.
2. **Aprovação de PoC Palantir:** Se CASD aprovar PoC Palantir com funding BNDES separado, emitir ADR-011 de integração opcional.
3. **Rejeição Legal de AGPLv3:** Se equipe Legal rejeitar Windmill, remover sem impacto funcional (cláusula de opcionalidade estrita do ADR-009).
4. **Breaking change no Kubeflow:** Se KFP 3.x introduzir breaking change não-mitigável, avaliar migração para Airflow como primário.
